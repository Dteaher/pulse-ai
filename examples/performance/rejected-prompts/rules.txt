Бизнес-модель, не исполняемый BPMN XML. Код создаёт XML, DI, references и проверяет XSD; не анализируй их самостоятельно.
Все явно описанные действия, включая доработку, повторную отправку и решение человека, — отдельные задачи соответствующих исполнителей. Сохраняй реальные роли раздельно, названия на языке текста. Задачи — краткий инфинитив, без повторения роли; source_text — точная подтверждающая выдержка, иначе inferred=true/confidence=confirmation_required. Условия и решения не выдумывать. Description сохраняет исходное описание.
Внутренние роли одной организации — lanes одного internal Pool; каждый независимый внешний участник — отдельный external Pool. Технические события/шлюзы принадлежат реальной роли, не вымышленной «Системе». Уникальные XML NCName ID во всей модели.
СНАЧАЛА связный локальный Sequence Flow каждого Pool от собственного Start через ВСЕ действия к End, включая альтернативы и возвраты. ПОТОМ Message Flow между разными Pool. Сообщения не заменяют локальный путь и не запускают завершённый процесс. Обмен между lanes одной организации — только Sequence Flow. Ни одного cross-pool Sequence Flow или same-pool Message Flow.
Человеческое действие не Start; принятие решения — user_task, затем gateway. Входящее сообщение, запускающее процесс, — Message Start, без дублированной первичной receive_task. Возврат в цикле идёт к повторной проверке/ожиданию, никогда к Start. Отправитель возврата ждёт исправление и повторяет проверку; предоставляющий исправляет и отдельно повторно отправляет документ.
Данные/результат решения → exclusive_gateway (decision_basis=data), разные понятные condition/name на ветвях либо один default. Альтернативы объединяются XOR, не Parallel Join. Задача имеет одну исходящую связь. Одновременные проверки → отдельные parallel split/join без условий; ВСЕ ветви достигают собственного join на разных входах.
Ожидание одного из будущих внешних сообщений → event_based_gateway (decision_basis=event), минимум 2 разных receive_task ИЛИ Message Catch Event, без conditions/default. Не смешивай эти виды successors; каждый имеет один локальный вход от gateway и соответствующее входящее сообщение. Уже полученный статус анализируется XOR, не event gateway. Получающий локальный процесс имеет путь к каждому ожидаемому ответу, включая отказ. Message Flow не направляется в gateway/end, не исходит из start/catch. Start/intermediate с event_definition=message — получение; остальные event_definition=none. Другие decision_basis=unspecified.
Обычные flows.name пустые, имена условий/шлюзов содержательны. Сохраняй циклы доработки документов и договора, все явно названные сообщения, отрицательные и положительные исходы. Не сокращай бизнес-граф ради размера ответа. Никаких пояснений вне JSON.
Одна receive_task/catch occurrence не может быть successor двух разных Event-Based Gateway. Если одно и то же сообщение ожидается в разных состояниях процесса, покажи отдельные occurrences с разными ID и входящими Message Flow, сохраняя смысл сообщения; после них можно объединить пути XOR. Сериализуй JSON компактно, без отступов и декоративных пробелов: экономь форматирование, не бизнес-действия или evidence.
