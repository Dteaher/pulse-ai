# Реальный тест GPT-5.5 / MultiAI после аудита backend

14 октября 2026 года. Production `.env` не изменялся: до и после каждого запуска проверена SHA-256 файла, без вывода его содержимого или ключей.

## Методика

Взята текущая конфигурация через `Settings` и `get_llm_provider`: primary `multiai`, `gpt-5.5`, reasoning `low`; резерв `vertex_gemini / gemini-2.5-flash`. Настройки не переопределялись.
Запросы `/api/process/generate` выполнены через настоящий FastAPI route и middleware с in-process HTTP transport. Внешний MultiAI transport реальный, без mock, cache hit или подмены ответов. Для снятия trace тестовый wrapper передавал `audit_trace` в исходную `generate_valid`; production API не изменён.

Полученные BPMN импортированы через «Открыть .bpmn» в локальном PULSE в Edge и действительно отображены bpmn-js. Это отдельный UI-импорт уже полученного результата, без повторного платного запроса из браузера. Генерацию через кнопку «Создать BPMN» в этом прогоне не дублировали.

Для каждого успешного запроса сохранены `input.txt`, `response.json`, `trace.json`, точные JSON обеих стадий, `performance.json` и XML. `provider_output` — типизированный результат адаптера, не полный необработанный HTTP-конверт.

## Сопоставление бизнес-логики с исходным текстом

### Простой

Все четыре действия сохранены: проверка документов (`node_check_documents`), принятие решения (`node_decide_complete`), регистрация (`node_register_application`), отправка отказа (`node_send_refusal`). Все назначены `participant_operator`.

`node_gateway_documents_complete` — data XOR. `flow_004`: «Документы полные» → регистрация → «Заявка принята в работу». `flow_006`: «Документы неполные» → отправка отказа → «Отказ отправлен». Ветки не соединяются AND. Отдельная задача принятия решения соответствует явной фразе исходного текста; её не добавлял Normalizer.

### Средний

Шесть клиентских действий: составить заявку, отправить её, получить запрос исправления, исправить документы, отправить исправленную заявку, получить подтверждение.
Шесть действий оператора: проверить документы, решить вопрос комплектности, отправить запрос исправления, получить исправленную заявку, зарегистрировать заявку, отправить подтверждение. Потерянных действий и чужих исполнителей нет.

- `node_company_documents_complete_gateway` — data XOR. Неполные документы идут по `flow_company_gateway_to_send_correction`; полные по `flow_company_gateway_to_register`.
- Точная точка возврата: `flow_company_receive_corrected_to_check`: `node_operator_receive_corrected_application → node_operator_check_documents`. Возврата к Start нет.
- На стороне клиента `flow_client_send_corrected_to_wait_merge` возвращает к XOR merge, далее Event-Based Gateway `node_client_wait_response_gateway`. Он ведёт только к двум Receive Task, без conditionExpression/default.
- Все четыре MessageFlow между разными Pool: `msg_initial_application`, `msg_correction_request`, `msg_corrected_application`, `msg_confirmation`.
- Подтверждение достигается только после регистрации; отправка запроса доработки не ведёт к преждевременному завершению.
- Допущение об отсутствии лимита повторов соответствует явно заданному тексту, новый лимит не придуман.

### Сложный

Сохранены **21 действие**: клиент — 8; оператор — 3; юридический отдел — 1; служба безопасности — 1; руководитель — 2; менеджер — 6. Получение первой заявки обозначено Message Start, а не потерянной Receive Task.

- Документы: `flow_company_documents_not_complete` → запрос → получение исправлений. `flow_company_receive_corrected_to_check` возвращает к `node_operator_check_completeness`. Полная заявка идёт через `flow_company_documents_complete` к проверкам.
- AND split `node_parallel_start_checks` запускает `node_legal_check_correctness` и `node_security_check_risks`, каждый у своей роли. Обе входят в `node_parallel_join_checks`. Только после join выполняется `node_leader_review_application_results`.
- XOR `node_gateway_application_approved`: `flow_company_application_rejected` → менеджер отправляет отказ → отказный End; `flow_company_application_approved` → менеджер составляет договор. Альтернативы не объединены AND.
- Отдельное решение по договору: `node_gateway_contract_agreed`. `flow_company_contract_not_agreed` → `node_manager_revise_contract` → повторная передача. `flow_company_retransfer_to_check_contract` возвращает точно к `node_leader_check_contract_project`, не к рассмотрению заявки и не к документам.
- Согласованный договор отправляется по `flow_company_contract_agreed` и завершается только после отправки.
- Клиент ждёт три внешних сообщения в `node_client_event_wait_messages`: доработка, отказ, договор. После договора сохранено `node_client_check_contract`.
- Пять MessageFlow сохранены, без сообщений между менеджером и руководителем одной компании. Передачи внутри компании — SequenceFlow.
- Исполнители: `participant_legal_department`, `participant_security_service`, `participant_leader`, `participant_manager`, `participant_operator`, `participant_client` совпадают с текстом. Новых ролей, лимитов, условий стоимости и дополнительных согласований нет.

**Логических дефектов LLM в этих трёх успешных ответах не обнаружено.** Это результат проверки конкретных, явно заданных текстов; не универсальная оценка GPT-5.5 для любых регламентов.

## Найденный дефект backend и исправление

В простой схеме условия в JSON и XML были правильными, но подписи ветвей в DI размещались далеко от своих стрелок:

- `flow_004` «Документы полные»: label x=1299, y=232,5, тогда как последний waypoint x=950, y≈226,67;
- `flow_006` «Документы неполные»: label x=864, y=75, последний waypoint x=950, y≈318,33.

Причина: `app/collaboration.py:build_collaboration`, вложенная `place_label`. Поиск свободного места горизонтальными сдвигами мог унести подпись за другие действия или в верхний коридор. Это **визуальное искажение привязки условия**, а не ошибка выбора condition/target моделью.

Регрессия `test_conditional_branch_labels_stay_near_their_own_target` воспроизвела дефект до исправления: расстояние подписи от конечной точки своей ветви превышало 400 px.
Для коротких условных ветвей добавлены предпочтительные свободные позиции рядом с их собственным target, в пределах Pool. Прежняя проверка отсутствия наложений сохранена. Узлы, участники, gateway, conditions и flow endpoints не менялись.

Все три XML пересобраны **из уже полученных ProcessDefinition**, без дополнительных LLM-запросов. `rebuild-report.json` подтверждает ноль семантических расхождений и ошибок; `polished.bpmn` — исправленный DI. Исходные `result.bpmn` и trace сохранены как доказательство обнаружения. Повторная визуальная проверка в Edge пройдена для всех трёх схем.

После исправления: **527 backend-тестов пройдено**, одно прежнее предупреждение TestClient. `git diff --check` пройден.

## Оставшиеся проблемы и оценка

1. **Устойчивость транспорта:** средний запрос один раз получил timeout MultiAI после 90 секунд; резерв вернул HTTP 429. Повтор с тем же текстом успешен. Без полного ответа нельзя приписать этот сбой качеству бизнес-разбора LLM. Не изменяли production timeout, бюджет или fallback ради успешного результата.
2. **Скорость:** сложный запрос занял 74 секунды; около 32,8 секунды пришлось на ambiguity analysis, около 41,1 секунды на extraction. Это единичные замеры, не p95. Локальные построение и проверки занимают миллисекунды и не объясняют основное ожидание.
3. **Читаемость:** сложная схема содержит длинные сообщения и возвраты. На «По размеру» текст мелкий из-за 6 дорожек и 34 узлов; для анализа нужен zoom. Исправление подписей не является полной переработкой layout.
4. **Границы доказательства:** нет универсального token simulator и гарантии произвольного NLP-разбора; проверены три конкретных текста и перечисленные бизнес-инварианты.

Оценка: **бизнес-семантика всех трёх полученных BPMN корректна; действия не потеряны; backend не изменил модель. Производственная надёжность и скорость API пока требуют внимания.**
