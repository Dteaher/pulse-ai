# Аудит сохранения бизнес-логики PULSE

Дата: 14 октября 2026 года. Проверен коммерческий репозиторий `pulse-ai`.
Исходный хакатонный репозиторий, production `.env`, модель, провайдер и ключи не изменялись.
Внешних LLM-запросов в этом аудите нет.

## Вывод

Причина ошибок не ограничивается MultiAI: шесть регрессионных случаев воспроизведены на вручную заданных моделях до исправлений (9 положительных эталонов прошли, 6 проверок дефектов упали). Ещё подтверждена потеря документального условия default flow в обоих сериализаторах.
После исправлений: **526 backend-тестов пройдено**, в том числе **35 новых**. Единственное предупреждение относится к устаревающему транспорту FastAPI TestClient, не к BPMN.

Девять положительных эталонов проходят весь `generate_valid` с одним локальным callback, без провайдеров, corrective и fallback. У всех ноль изменений нормализации и ноль расхождений с XML. Дополнительно проверена вложенная AND-синхронизация. XML девяти эталонов и существующего сложного процесса импортируется установленным `bpmn-moddle` из зависимостей bpmn-js: 10 файлов, ноль предупреждений. Это проверка парсера, не новый визуальный браузерный прогон.

| Участок | Поведение | Граница проверки |
|---|---|---|

| `preflight.py:prepare`, `analyze`, `attach_assumptions` | Объединяет допущения и ответы; критичные вопросы блокируют построение. | Не добавляет бизнес-действия. |
| `models.py:ProcessPatch.apply` | Применяет модельный patch; при корректировке защищает подтверждённые действия от удаления. | Это новая модельная кандидатура, не детерминированный Normalizer. |
| `changes.py:preserve_ids` | Восстанавливает уникально совпавшие ID и перенаправляет ссылки на восстановленные ID. | Логическое редактирование выполняет модель; ID reconciliation не доказывает соответствие команде. |
| `commands.py:rename_command` | По точной одноимённой команде меняет только название одного действия/роли. | Затем стандартный pipeline. |
| `notation.py:polish_process` | Переклассификация явно событийного XOR; вставка XOR merge; удаление inferred waiting placeholder без evidence и сообщений; свёртка стартового Receive. | Каждое изменение видно в точном diff. Дополнительные бизнес-сведения запрещают небезопасную свёртку. |
| `repair.py:apply_repair`, `assert_preservation` | По ошибкам применяет ограниченный LLM structural patch: endpoints, технический gateway, duplicate flow, cross-pool message. | Полная повторная валидация, защищённые объекты и контроль циклов. Проверка не является доказательством произвольной бизнес-семантики patch. |
| `pipeline.py:generate_valid` | После ошибок может запросить новую модельную кандидатуру, затем fallback. | Эталонные тесты отключают эти пути (`max_retries=0`, без provider). Ошибка соответствия XML не запускает модельное «исправление». |

Один старый JSON-эталон ожидал преобразование Reply в событийный шлюз без явного указания его природы. В `examples/controlled-loops/reference.json` добавлено `decision_basis=event`. Названия, условия, роли, действия и возвраты не менялись. Контрольная сумма нормализованного результата **совпала с прежней golden checksum**; manifest и проверки не ослаблялись.

## Диагностика по стадиям

`generate_valid(..., audit_trace=[])` сохраняет:

1. `provider_output`: точную ProcessDefinition на входе pipeline после адаптера.
2. `normalization`: итоговую модель и точные field-level изменения, включая удаления, ID, evidence, условия, участников и MessageFlow.
3. `validation`: структурные и семантические замечания, включая coverage при его выполнении.
4. `bpmn_xml`: итоговый XML и независимые расхождения.

`logic_audit.py:compare_process_xml` не использует importer как источник истины. Сверяет наборы и типы узлов, события, названия, evidence, decision_basis, входы/выходы, gatewayDirection, default, source/target/condition/labels переходов, дорожки и принадлежность Pool, MessageFlow, описание и допущения.
`confidence` и `inferred` — метаданные редактирования, не обещанные поля BPMN; они остаются в JSON trace.

`require_xml_fidelity` включён в обоих сериализаторах и pipeline. Расхождение даёт `BPMN_SEMANTIC_DRIFT` и блокирует результат, не исправляя XML или исходную модель. Trace не добавлен в публичный API и по умолчанию не записывается в логи: он содержит бизнес-текст.

Из каталога `backend` офлайн-аудит сохранённой модели:

```sh
../.venv/Scripts/python.exe -m tools.audit_logic ../examples/controlled-loops/reference.json --output ../.runtime/backend-logic-audit/new-run
```

Выход: `input.json`, `normalized.json`, `trace.json`, `report.json`, успешный `result.bpmn`. Провайдер не создаётся, внешние запросы не выполняются.

## Новые проверки

`tests/test_backend_logic_audit.py`: **35 тестовых случаев**.

- Последовательность; XOR с разными завершениями; AND split/join; XOR внутри AND; AND внутри XOR; возвраты документов и договора; отклонение; два Pool с MessageFlow.
- Вложенный AND внутри AND; запрет завершения ветви до синхронизации.
- Все подтверждённые дефекты из таблицы, default в обоих сериализаторах.
- Преднамеренная порча XML: потеря действия, замена XOR на AND, ветки/условия/default, входящие связи, роли/Pool, раннее завершение, лишний flow, точка возврата и MessageFlow.
- Неизменность входного объекта; полные stage snapshots; сохранение диагностик офлайн; ошибочный XML блокируется без LLM retry.

Команда полного прогона из `backend`: `../.venv/Scripts/python.exe -m pytest tests -q`.
Итог: **526 passed, 1 warning**. `git diff --check` пройден.
Локальные подробные артефакты: `.runtime/backend-logic-audit/summary.json`, папки эталонов, `moddle-import.json`.

## Что доказано и что нет

Для проверенных канонических эталонов сохранение структуры и бизнес-переходов доказано тестами. На этапе нормализованная модель → XML дополнительно действует runtime guard. Ошибки конкретных нормализационных эвристик исправлены и закреплены регрессиями.

Не заявляется формальная гарантия для всех возможных ProcessDefinition и всех BPMN 2.0 конструкций. Сохраняются поддерживаемый subset, ограничения структурированных AND-пар и лексическая проверка некоторых исходов. Нет полного token simulator, доказательства завершения циклов или истинности свободнотекстовых условий. Нормализатор по-прежнему делает перечисленные технические преобразования; trace делает их проверяемыми, но сам diff не доказывает эквивалентность произвольных графов.

Без сопоставления исходного текста с реальным ответом модели нельзя установить, правильно ли LLM выделила процесс. Этот аудит доказывает существование и исправление backend-дефектов, а не отсутствие ошибок MultiAI/LLM. Новая диагностика позволяет локализовать следующий инцидент: неправильная входная модель, изменение в нормализации либо расхождение при XML-сборке.
