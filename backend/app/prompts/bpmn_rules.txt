ОБЯЗАТЕЛЬНО: Message Flow не заменяет Sequence Flow. Сначала построй полный граф управления КАЖДОГО Pool отдельно от сообщений; затем добавь message_flows. Клиент после отправки должен иметь путь и к доработке, и к каждому конечному исходу. Запрещено оставлять «Получить договор» или «Получить отказ» без входящей Sequence Flow, даже если к ним уже приходит Message Flow. Запрещено направлять отправку заявки только к доработке — это делает остальные исходы недостижимыми.

Профессиональная BPMN collaboration:
- Сохраняй всех различных явно названных исполнителей отдельными participants/lanes. Не объединяй роли лишь потому, что обе принимают решения или работают с одним документом. Проверяй исполнителя каждого действия по исходной фразе.
- Решение, которое принимает человек, — отдельная user_task этого исполнителя, затем gateway маршрутизирует результат. Сам gateway не заменяет явно описанное бизнес-действие принятия решения.
- При возврате документа на доработку обе стороны продолжают свои локальные процессы: возвращающая сторона ждёт новую версию, получает её и повторяет проверку. Не завершай её End Event после возврата, если исходный текст требует повторного получения. Message Flow не создаёт новый токен после End Event.
- Каждый Pool содержит свой самостоятельный граф Sequence Flow со start_event, задачами и end_event. Внешний Pool раскрыт, его действия не теряются; не связывай процессы sequence flow.
- flows — ТОЛЬКО Sequence Flow внутри одного Pool. message_flows — отдельные связи сообщений между узлами разных Pool. Сообщение нельзя направлять в gateway/end_event или отправлять из start_event. Используй send_task / receive_task для обмена; Start Event может получать сообщение, когда исходный текст явно содержит триггер получения. receive_task ждёт сообщения, обычный user_task выполняет человеческое действие.
- При возврате документов оператор отправляет запрос, клиент получает его, дорабатывает и отправляет исправленные документы; оператор ожидает их получение и возвращается к исходной проверке. В ожидающем Pool используй Event-Based Gateway и receive_task для реально описанных альтернативных сообщений; повторная отправка возвращает клиента к ожиданию. Это описательная бизнес-модель, без сложных event definitions. Каждое сообщение подтверждено исходной логикой, не добавляй лишнего обмена.
- Первое человеческое действие НЕ Start Event: start_event «Начало процесса» → user_task «Подать заявку». Настоящий явно описанный триггер («Получена заявка», «Наступил срок проверки») можно использовать как старт. Не выдумывай потребность/событие, отсутствующие во входе.
- Короткие задачи в инфинитиве («Проверить заявку»), без повторения роли из lane. source_text сохраняет полную исходную фразу. XOR split — вопрос, XOR join — короткое объединение; parallel split/join обозначают одновременность, не альтернативу.
- name обычных Sequence Flow пустой. Подписывай условия XOR и только существенные бизнес-переходы. Все видимые name на языке входа, никаких технических submit, legal done, to decision. ID могут быть английскими. Не придумывай название компании: если не указано, нейтральное «Организация»; используй предметный контекст (например «Энергоснабжающая компания»), если он ясно задан.

Перед выдачей проверь отдельно каждый Pool: минимум один start_event и один end_event. Даже у send_task/receive_task должна быть входящая Sequence Flow (от старта/задачи/gateway) и исходящая Sequence Flow к следующему действию/концу. Message Flow не считается входом/выходом для связности процесса. Нельзя оставить отправителя без продолжения или получателя без предшественника. Все end_event принадлежат тому же Pool, что завершаемая ветка.
Общий шаблон двух процессов (это пример правила, не готовая бизнес-схема): внешний Start → Отправить запрос → Получить ответ → End; внутренний Message Start «Получен запрос» → Выполнить действие → Отправить ответ → End. Sequence Flow соединяет только эти соседние шаги своего Pool. Отдельные Message Flow: внешнее «Отправить запрос» → внутренний Message Start; внутреннее «Отправить ответ» → внешнее «Получить ответ». Если есть возврат на доработку, внутри каждого Pool также нужен свой полный цикл ожидания/получения/доработки, а не только пунктирное сообщение. Не добавляй неподтверждённые исходным текстом конечные исходы. Перед ответом проверь, что каждый созданный узел включён в flows, а Message Flow направлен в принимающую задачу или Message Start, никогда в gateway.

Ожидание внешних сообщений — Send Task → event_based_gateway → альтернативные receive_task ИЛИ альтернативные intermediate_event с event_definition=message. Не смешивай receive_task и catch events в одном event gateway. У event_based_gateway decision_basis=event, один вход (при возврате добавь отдельный XOR merge перед ним), минимум два различных ожидания, никакого condition/is_default на исходящих flows. Событие/receive successor получает Sequence Flow только от этого event gateway. Первый пришедший ответ определяет ветку; техническая задача «Ожидать ответ» не нужна. После доработки и повторной отправки верни локальный поток к ожиданию. Каждое получение сообщения имеет соответствующий Message Flow из другого Pool.
Если сначала получено одно общее сообщение, а затем анализируется уже полученный статус/данные, используй exclusive_gateway с decision_basis=data: это не конкуренция будущих сообщений. Различай ожидание и анализ результата по контексту.
Старт процесса входящим сообщением — start_event с event_definition=message, Message Flow направлен прямо в него, затем первая бизнес-задача. Не дублируй первичное получение отдельным receive_task после обычного Start. Повторное получение в цикле остаётся receive_task; Message Start Event нельзя использовать как цель возвратной Sequence Flow.
Для exclusive_gateway укажи decision_basis=data; для event_based_gateway — event; для прочих узлов — unspecified. event_definition=message допустим только у start_event и intermediate_event (Intermediate Catch Message Event); иначе none. Альтернативные ветви данных, сходящиеся к общей задаче, при необходимости явно объединяй отдельным converging exclusive_gateway, а не parallel join.

Контролируемые циклы допустимы. Возврат на исправление или повторное согласование — Sequence Flow назад внутри своего Pool. У действия может быть несколько входов; XOR может одновременно объединять повторный вход и разделять альтернативы, если условия всех исходящих ветвей заданы. При необходимости используй отдельные XOR merge и split. Альтернативные пути обхода согласования и одобрения объединяются XOR или входами обычной задачи, никогда parallel join. Parallel join объединяет только независимые одновременно запущенные проверки.
Передача работы между сотрудниками/дорожками ОДНОЙ организации, включая руководителя и менеджера, — только Sequence Flow. Не создавай message_flows для внутреннего согласования, даже если текст говорит «отправляет руководителю». Send/receive не требуют добавления Message Flow, когда это внутренняя передача работы; предпочитай user_task для внутреннего действия. Message Flow создавай только при пересечении явно разных pools.
Если corrective context содержит errors, исправь указанные code и ID, сохрани остальные действия и все локальные flows. UNREACHABLE_NODE / ORPHAN_NODE: добавь недостающую локальную Sequence Flow, не сообщение. SAME_POOL_MESSAGE_FLOW: удаляй ошибочное внутреннее сообщение, сохраняй локальную передачу работы. CROSS_POOL_SEQUENCE_FLOW: замени межпроцессную связь сообщением и отдельно восстанови полный локальный путь каждого Pool. PARALLEL_JOIN_MISMATCH: проверь собственный join параллельного split; не объединяй альтернативные XOR-ветви параллельно.

Сохраняй все явно описанные действия повторной отправки и передачи работы. Исправление документа и его повторная отправка — разные задачи, если оба действия названы в тексте. Для обмена исправленными документами между разными Pool покажи отдельную повторную отправку, соответствующее получение и Message Flow между ними; не заменяй получение исправлений обычной задачей «Продолжить». Внутреннюю повторную отправку на согласование покажи отдельной user_task и Sequence Flow назад к задаче согласования, без Message Flow между дорожками. Исправляя связность, не удаляй исходные бизнес-действия и сообщения.
